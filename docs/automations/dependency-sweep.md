# Dependency Sweep Automation

The dependency sweep is a scheduled repository-maintenance role for dependency
pins that Dependabot does not reliably update. It should keep development
tooling and package-manager state reproducible while preserving the dependency
posture documented in [`docs/dependencies.md`](../dependencies.md).

The automation must read `docs/automations/README.md`, this document, and
`docs/dependencies.md` before making changes. Human feedback on any output it
produces, including pull request comments, review decisions, failed validation,
or inbox follow-ups, should be reviewed and used to update these guardrails
before repeating the same class of change. Automation-authored pull request
comments must start with the stable prefix `Codex automation note:`.

## Dependabot First

Start every run by reviewing open pull requests created by Dependabot. If a
Dependabot pull request is mechanical, aligned with the dependency posture, and
passing CI, move it to GitHub auto-merge.

Do not use auto-merge for Dependabot pull requests with broad version jumps,
unclear lockfile churn, failing or missing validation, compatibility risk, or
other changes that need human review. Leave those pull requests open and add a
short `Codex automation note:` comment when the reason is not already clear.

If any Dependabot pull request is moved to auto-merge, wait until GitHub merges
it and the repository primary branch contains the merge before creating or
updating automation-owned dependency branches. When multiple Dependabot pull
requests are accepted, wait for all accepted merges, fetch the updated primary
branch, and rebase the current workspace onto it before continuing.

## Scope

The sweep owns dependency maintenance that is not covered well by Dependabot:

- non-Rust tool versions in `mise.toml`, including Node.js, Zizmor, and
  cargo-installed development tools;
- the pnpm `packageManager` pin in `package.json`;
- pnpm lockfile refreshes and transitive Node dependency updates;
- `pnpm-workspace.yaml` hardening settings;
- documentation updates needed to keep dependency posture and automation
  instructions accurate.

Dependabot remains the default owner for Rust crate dependency updates, GitHub
Actions dependency groups, and direct Node dependency version bumps in
`package.json`.

## Pinning Rules

Pin non-Rust tools exactly. Do not introduce `latest`, `lts`, branch names,
broad version ranges, or mutable tags for durable tooling inputs.

Rust is the explicit exception. Keep `rust.version = "stable"` in `mise.toml`
unless the repository's Rust support policy changes. The sweep may update the
comment documenting that exception, but it should not replace the stable channel
with a dated Rust version.

Node.js should track the latest LTS line after a one-week cooldown. Local
bootstrap should select pnpm through Corepack from the
`package.json#packageManager` pin; do not add a separate pnpm pin to
`mise.toml`. CI workflows should install pnpm with a pinned `pnpm/action-setup`
action instead of Corepack.

## Workflow

For automation-owned updates:

- use authoritative upstream release metadata;
- apply at least a one-week cooldown before adopting new tool or package-manager
  releases;
- update manifests and lockfiles together;
- keep package-manager lockfiles generated by their package managers;
- run formatting and relevant validation before opening or updating a pull
  request.

## Pull Requests

Use one branch and one pull request per logical dependency domain. Pull requests
from this automation must include the `A-deps`, `C-automation`, and `codex`
labels. Do not enable auto-merge for high-risk updates, failed validation,
unclear release notes, or non-mechanical migrations.

Each pull request should summarize:

- old and new versions or lockfile refresh scope;
- cooldown decisions;
- validation commands and results;
- any Dependabot pull requests reviewed, merged, or intentionally left alone.
