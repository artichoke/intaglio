# Dependency and Supply Chain Posture

This repository keeps dependency surfaces small, pinned, and auditable. Every
dependency should have an owner, a reason to exist, and a reproducible update
path.

## Principles

- Prefer Rust standard library code and repo-local helpers when behavior is
  small, stable, and easy to test.
- Add dependencies only when they reduce more risk or complexity than they
  introduce.
- Pin direct development tooling dependencies exactly.
- Do not use mutable selectors such as `latest`, `lts`, branch names, broad
  version ranges, or floating tags for durable tooling inputs.
- Rust is the explicit exception: this Rust library intentionally tracks the
  `stable` Rust channel in `mise.toml` because the crate is expected to build on
  the current stable compiler.
- Apply a one-week cooldown before adopting newly released toolchain and
  package-manager versions.
- Keep generated artifacts reproducible from repo-owned or immutable pinned
  inputs.
- Prefer structured parsers for structured files.
- Keep package-manager lockfiles owned by their package managers. Exclude
  `pnpm-lock.yaml` and `pnpm-workspace.yaml` from Prettier because they are
  package-manager and toolchain-managed files.

## Ownership

Each dependency belongs to one of these surfaces:

- Rust crate dependencies used by the library or its tests;
- toolchains used to run repository automation;
- repo-local development and lint tooling;
- Node formatting tooling;
- CI actions and workflow tooling;
- generated artifact inputs, when present.

The owning surface determines where the pin lives. Rust crate compatibility
requirements belong in `Cargo.toml`. Concrete Rust dependency selections belong
in `Cargo.lock` when the repository has one. Language runtimes and bootstrap
tools belong in `mise.toml`. Node package-manager state belongs in
`package.json`, `pnpm-lock.yaml`, and `pnpm-workspace.yaml`. Prettier must not
rewrite the pnpm lockfile or workspace config.

## Toolchains

`mise.toml` is the canonical local toolchain manifest. Non-Rust tools in
`mise.toml` must be pinned to exact versions. Rust remains pinned to the
`stable` channel by design; do not replace it with a dated compiler version
unless the repository's Rust support policy changes.

Node.js should track the latest LTS line after cooldown. Local bootstrap uses
Corepack to select pnpm from the exact `package.json#packageManager` pin rather
than a separate `mise.toml` tool pin. CI workflows should install pnpm with a
pinned `pnpm/action-setup` action instead of Corepack.

## Language Dependencies

Node dependencies are only for text formatting. Prettier is the expected direct
Node dependency because it owns deterministic formatting for Markdown, YAML,
JSON, and related text surfaces.

Rust dependencies should stay close to the standard library unless the
dependency is part of an intentionally trusted ecosystem or is clearly justified
by library behavior. Direct dependencies are the enforceable policy boundary.
Transitive dependency sets should be understood through their direct trusted
roots rather than manually allowlisted one package at a time.

Known-vulnerability checks complement dependency classification but do not
replace it.

## Freshness

Freshness checks may resolve upstream state over the network when the upstream
source is authoritative and stable enough for automation. If upstream state is
ambiguous, prefer reporting the ambiguity over guessing.

## Enforcement

Dependency changes should preserve this posture, keep lockfiles generated by
their package managers, and run the relevant formatting, linting, and tests
before a pull request is marked ready.
